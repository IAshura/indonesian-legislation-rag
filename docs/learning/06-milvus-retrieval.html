Bab 06 · Milvus

Menyimpan 63.231 Vektor di Milvus — Database yang “Cari Mirip”

Vektor yang sudah dibuat perlu tempat penyimpanan yang bisa mencari tetangga terdekat dengan cepat. Proyek ini memakai Milvus versi standalone yang berjalan penuh di komputer sendiri lewat Docker. Bab ini bedah insert_milvus.py dan smoke_milvus.py — termasuk jebakan indeks asinkron yang nyata dialami.

⏱️ ±15 menit baca File: insert_milvus.py (207 baris) · smoke_milvus.py (84 baris) Koleksi: legislation_norma_v1 & legislation_norma_q3e06b

1. Konsep: kenapa butuh database khusus?

Mencari “dokumen paling mirip” = mencari vektor terdekat dengan vektor pertanyaan. Kalau datanya 63 ribu vektor float32 1024-dimensi (≈260 MB), komputer biasa masih kuat membandingkan semuanya secara langsung (exact search — Bab 08). Tapi database vektor memberi tiga kemudahan serius: indeks ANN (Bab 08) yang skala ke jutaan vektor, metadata & filter tersimpan bersama vektor, dan persistence — data hidup walau program ditutup.

Milvus standalone terdiri dari tiga kontainer Docker yang bekerja sama:

KomponenPeran untuk pemula
etcd“Buku catatan metadanya” — menyimpan struktur koleksi, skema, status indeks
minio“Gudang file” — tempat data vektor & log segmen disimpan
standalone“Otaknya” — menerima insert/query (port 19530), mengeksekusi pencarian

Setup mesin ini (dokstring insert_milvus.py baris 6–8): Docker Desktop + compose di C:\milvus — docker compose up -d untuk start, docker compose down untuk stop. Data persisten di C:\milvus\volumes (folder etcd, minio, milvus — ada di mesin ini saat situs ini dibuat).

Dua mekanisme anti-dobel: (1) guard baris 160–161 — kalau jumlah entitas sudah sama dengan jumlah record, insert dilewati sama sekali; (2) insert perlahan-lahan 1.000 record per batch (INSERT_BATCH = 1000, baris 47) dengan progres tercetak, lalu flush() (paksa tulis ke penyimpanan) dan load() (muat koleksi ke memori agar bisa dicari).

Mengapa dipisah? Dimensi berbeda (2560 vs 1024) dan “ruang makna” berbeda. Mencari vektor 0.6B di koleksi 4B akan memberi skor omong kosong — inilah aturan besi model index = model query diterapkan sampai ke nama koleksi.

5. Pilihan indeks saat membuat koleksi (baris 52–67)

pipeline/insert_milvus.pybaris 52–67
INDEX_CONFIGS = { "hnsw": { # graph ANN — default; ef = lebar pencarian graph saat query "index": {"index_type": "HNSW", "metric_type": "IP", "params": {"M": 16, "efConstruction": 200}}, "search": {"metric_type": "IP", "params": {"ef": 64}}, }, "ivf": { # ANN berbasis klaster; nprobe = jumlah klaster yang diperiksa "index": {"index_type": "IVF_FLAT", "metric_type": "IP", "params": {"nlist": 1024}}, "search": {"metric_type": "IP", "params": {"nprobe": 16}}, }, "flat": { # brute force / exact — bandingkan SEMUA vektor, selalu benar "index": {"index_type": "FLAT", "metric_type": "IP", "params": {}}, "search": {"metric_type": "IP", "params": {}}, },}

Tiga mode tersedia lewat flag --index {hnsw,ivf,flat}; default hnsw. Semuanya memakai metrik IP (inner product) karena vektor kita L2-normal — dot product = cosine. Bab 08 membedah ketiganya lebih dalam, termasuk flag --rebuild-index yang mengganti indeks tanpa insert ulang (baris 131–139). Instrumen utamanya: index_type_of() (baris 80–83) yang membaca indeks AKTIF dari koleksi — FLAT bila tanpa indeks.

Detail cerdas di sini: parameter pencarian mengikuti indeks yang benar-benar aktif di koleksi (baris 189–191), bukan flag yang diketik — komentar kode menyebutnya “demo tetap benar apa pun --index yang diketik”. Demo menerima pertanyaan, meng-encode-nya dengan encoder model aktif, mencari top-5, dan mencetak skor + chunk + parent — lalu pesan “langkah berikutnya: join parent_id → parents.jsonl → LLM”.

7. Smoke test: smoke_milvus.py — self-query

Sebelum memercayai hasil demo, kesehatan sistem diuji dengan cara paling objektif (dokstring: “terpisah dari kualitas model”): ambil beberapa vektor langsung dari embeddings.npy, carikan tetangganya di Milvus, dan pastikan top-1 = vektor itu sendiri dengan skor ~1,0:

pipeline/smoke_milvus.pybaris 64–75 (inti)
rng = random.Random(42)picks = rng.sample(range(len(ids)), a.n)for i in picks: res = col.search([vecs[i].tolist()], anns_field="embedding", param=param, limit=a.top, output_fields=["chunk_id"]) hit_self = hits[0].entity.get("chunk_id") match = hit_self == ids[i]["chunk_id"] ok += match status = "OK " if match else "SALAH" print(f" [{status}] {ids[i]['chunk_id']}")

Test ini memisahkan dua kemungkinan kegagalan: kalau self-query gagal, yang rusak adalah infrastruktur (koneksi, koleksi, indeks, insert); kalau self-query lulus tapi pertanyaan bahasa manusia tetap jelek, yang bermasalah adalah kualitas model/embedding — bukan Milvusnya. Kode keluar 1 bila ada satu saja yang SALAH (baris 80). Parameter pencarian mengikuti indeks aktif: HNSW → ef 32, IVF_FLAT → nprobe 64 (baris 53–59).

8. Jebakan nyata: indeks dibangun belakangan (asinkron)

Kasus nyata dari README-retrieval.md §5: beberapa detik setelah insert/flush, indeks HNSW belum selesai dibangun — query bisa mengembalikan hasil yang salah (demo pertama mengembalikan chunk berbeda dengan skor lebih rendah; run berikutnya sudah identik dengan exact search). Solusinya: tunggu indeks selesai dan jalankan smoke_milvus.py dulu sebelum memercayai hasil. Milvus membangun indeks di latar belakang; “selesai insert” ≠ “indeks siap”.

9. Ringkasan bab

  • Milvus standalone = Docker 3 kontainer (etcd + minio + standalone), data di C:\milvus\volumes.
  • Skema: 11 field — PK otomatis, 9 metadata dari ids.jsonl, 1 FLOAT_VECTOR (dim dari meta.json).
  • Insert batch 1.000 + guard “sudah lengkap → jangan insert ulang” + flush + load.
  • Dua koleksi terpisah per model: legislation_norma_v1 (4B) & legislation_norma_q3e06b (0.6B).
  • smoke_milvus.py: self-query top-1 = dirinya sendiri = syarat percaya sistem.
  • Jebakan: indeks asinkron — tunggu build selesai sebelum percaya hasil.
Istilah baru bab ini: Milvus, Docker, koleksi, ANN, metrik IP, flush, smoke test, self-query.
